## Gotchas that cost time to rediscover

- `npm run dev` wants port 8080, which collides with the user's Ekami Auto project.
  Use `npx vite --port 8090 --strictPort`.
- Scripts reading Supabase creds need `node --env-file=.env ...` or they crash with
  `supabaseUrl is required`.
- `npx supabase db query --linked` **mangles multi-line SQL** — pass `-f file.sql` instead.
- **Never run `supabase db push`** — remote migration history is untracked; it would replay ~150
  migrations.
- Scripts must live inside the repo to resolve `node_modules` (`$CLAUDE_JOB_DIR/tmp` cannot import
  `@supabase/supabase-js`).
- `ALTER TABLE` on `songs` / `artists` can deadlock against live traffic (the user hit this). A
  deadlock is safe to retry; set `SET lock_timeout = '5s';` first so a migration fails fast instead
  of freezing the site behind a lock.
- `bara.africa` does not resolve (DNS). `www.baraafrika.com` is the working domain. Pre-existing.

## Do not re-propose

The user rejected these explicitly; re-raising them wastes their time:

- **Key-based i18n** (`t()` + locale files) — "millions of translation files" is exactly what they
  don't want to manage.
- **A hybrid** (i18n for the app shell + machine translation for user content) — rejected outright.
  They optimise for **zero maintenance** over translation quality.

Note the irony worth remembering but not re-litigating: the repo *already contains* a complete
react-i18next setup at `src/lib/i18n.ts` with seven genuine locale files in `src/locales/` (886 keys,
94–98% translated, real Kinyarwanda), disabled by one line — `lng: 'en'`. Only ~9% of the UI calls
`t()` though (marketplace: 0 of 30 pages), which is why it was never viable. **Keep `src/locales/`
in the repo** as a free fallback; do not delete it.
