# Streams Migrations Tracking

Every `supabase/migrations/*.sql` file added by a Streams phase PR (see `STREAMS_MASTER_PLAN.md`) is logged here as it's added. None of these are applied automatically — per standing project convention, migrations are listed for review and applied separately, never via `supabase db push`. A dedicated later phase will review this list, resolve any ordering/overlap issues, and apply everything in one pass rather than one-off per phase.

**Process:** whenever a phase branch adds a migration file, add a row below in the same commit.

**Update 2026-08-05:** `20260509_ebooks.sql` (pre-existing, predates this multi-phase project) was discovered unapplied while seeding ebooks data for Phase 9 — the live DB had no `ebooks` table or bucket despite the frontend being coded against it since May. That plus rows 1–8 below were all applied by the user on 2026-08-05 and verified (schema + RPCs queried directly via the Supabase REST API, and the Phase 9 seed script ran successfully end-to-end against the live `ebooks` table/bucket afterward). `podcasts`/`podcast_episodes`/`movies`/`movie_watchlist` (from `20260319_sprint7_test_data.sql`) were confirmed already live before this pass.

## Notes (rows 1–8 above applied 2026-08-05 — kept for history/reference on future phases)

- Applied in the order listed above (filename date order already matched dependency order across phases).
- `20260805_harden_play_counting.sql` depends on `songs` and `play_history` already existing (they do, from earlier migrations) — no new dependency risk.
- `20260804_consolidate_song_artists_junction.sql` is almost certainly already applied on the live DB by hand (the table is in active use across the app) — running it is still safe (idempotent guards throughout) but double check `song_artists` row counts before/after to confirm nothing double-applies unexpectedly.
- `20260804_songs_draft_publish_state.sql`: purely additive columns, safe to apply any time. Note the two same-day Phase 5 files (`_consolidate_song_artists_junction` and `_songs_draft_publish_state`) are independent of each other and can apply in either order.
- `20260804_artist_claim_flow.sql`: **before applying**, run `SELECT user_id, COUNT(*) FROM artists WHERE user_id IS NOT NULL GROUP BY user_id HAVING COUNT(*) > 1;` — if that returns any rows, the `ADD CONSTRAINT artists_user_id_unique UNIQUE (user_id)` statement will fail and those duplicates need manual resolution (merge or null out the extras) before this migration can land.
- `20260805_content_moderation.sql` **must apply after** Phase 5's `20260804_songs_draft_publish_state.sql` — its takedown path does `UPDATE songs SET status = 'draft'`, which needs that column to exist first. Filename order already puts it after (804 < 805), but double check if phases land out of order.
- `20260805_podcasts_creator_and_storage.sql` has no ordering dependency on the other rows — `podcasts`/`podcast_episodes`/`podcast_listen_history` are pre-existing tables from `20260319_sprint7_test_data.sql`, untouched by any other row in this list. Safe to apply independently.
- `20260805_movies_watch_and_storage.sql` should apply alongside (order doesn't matter relative to) row 2 (`20260804_consolidate_song_artists_junction.sql`) — together they're what finally makes `AdminMovies.tsx` work: row 2 added `producers`/`writers`/`actors`, this one adds `stream_url`. Applying only one of the two still leaves admin movie create/edit broken.
- `20260805_ebooks_reader_and_reads.sql` depended on `public.ebooks` existing — `20260509_ebooks.sql` was applied first to satisfy that. The column rename is guarded to no-op if `read_count` already exists or `download_count` doesn't, so it's safe to re-run.
- `20260805_admin_command_center.sql` (row 9, **not yet applied**) has no dependency on rows 1–8 — safe to apply independently. The `is_seed` backfill is a plain `UPDATE ... WHERE id::text LIKE '<prefix>-%'`, safe to re-run.
- Re-check this file at the start of every new phase for anything added since the last apply pass — new phases will add new unapplied rows below this point.

## Rows 10–11 (Phase 13 — pre-launch security gate, NOT yet applied)

- **Apply order does not matter between rows 10 and 11** — row 11 redefines its own copies of the `clerk_user_id()`/`is_active_admin()` helper functions rather than depending on row 10 having run first, specifically so the two can apply in either order (or the same transaction) safely.
- **Both require the client-side migration in the same PR to already be live** (every creator/admin write path now sends a Clerk-JWT-authenticated Supabase client instead of the anon-key client). Applying either migration first and shipping the client change later — or not at all — will break song/album/artist/playlist/podcast create, edit, and delete for every user until the client change ships too.
- **Run the PR's manual QA checklist against a real signed-in Clerk session in staging before applying either to production.** Neither migration was (or could be) tested with a live Clerk session in the dev sandbox this was written in.
- If row 9 (`20260805_admin_command_center.sql`, `is_seed` columns) is applied to `songs` in the future, remember to add `is_seed` to row 10's `GRANT UPDATE (...) ON public.songs` column list — anything left off that list silently fails to update for authenticated clients, by design.
- Row 9 also depends on `admin_users` existing with `user_id`/`is_active` columns (from `20241211_create_admin_users_secure.sql`) — same table rows 10/11's `is_active_admin()` helper reads from. If that table's shape ever changes, both this row and row 9 need updating together.
